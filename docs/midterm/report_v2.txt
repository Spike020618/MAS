# 一、研究内容简介
## 1. 选题背景
大语言模型能够根据自然语言指令完成推理、检索、分析和内容生成等任务，为构建能够协同解决复杂问题的多智能体系统提供了技术基础。在多智能体系统中，多个Agent可以分别分析任务、提出候选方案、检查他人判断并形成共同决定。与单次模型调用相比，这种方式能够保留不同的分析路径，也为发现遗漏信息和纠正错误提供了机会。因此，如何组织多个Agent之间的信息生产与交互，是本课题开展研究的出发点。
已有协作方法主要通过独立采样、多数投票、角色分工或多轮辩论形成最终答案。自一致性方法对多条推理路径进行聚合，多智能体辩论让模型实例交换判断，角色协作框架则把复杂任务分配给不同职责的Agent[1-3]。这些方法说明，协作结构会影响信息的产生和使用方式。然而，Agent数量增加并不必然带来新的有效信息；如果多个Agent依赖相同模型和相同上下文，其错误也可能具有较强相关性。
在实际执行中，系统还面临资源投入与信息价值不匹配的问题。短答、完整分析、额外核验和参考同伴需要不同的调用次数与Token预算。若系统只观察最终答案，便难以判断一致意见来自独立分析、重复生成还是同伴影响。对同一份报告增加完整字段，也不能直接说明其中证据可靠或推断正确。因此，本课题将资源行动、报告内容及其对集体决策的作用共同纳入研究范围。
影视搜索推荐为研究提供了具体应用场景。用户可能同时提出类型、年份、已看影片排除等明确条件，也可能只给出较为模糊的兴趣描述。推荐系统需要从真实目录中召回候选，对偏好和影片证据进行分析，并输出可以解释的推荐结果。若直接让模型生成片名，可能出现目录不存在、约束不满足或推荐理由缺少来源的问题；若只依赖词法匹配，又难以充分利用对话中的偏好信息。研究可靠的多Agent信息处理机制，并将其接入已有影视系统，具有明确的工程需求。
@@2
现有多智能体研究中，一个需要进一步讨论的问题是“讨论是否真正改进了判断”。Agent可以在看到同伴报告后改变结论，但改变可能来自新增证据，也可能来自对多数意见的迎合。反过来，Agent保持原有意见，既可能是保留了正确的少数判断，也可能是拒绝接受有效纠正。仅以一致率或结论变化次数评价共识过程，无法区分上述情况。本课题因此关注报告中的信息来源、主张指向及更新理由，并以外部任务结果检验这些过程是否有价值。
从机制设计角度，可以在行动前公布规则，明确完整报告、核验及纠正等行为怎样影响系统信用，同时记录其资源成本。前期工作已经实现了公开合同与行动执行，并观察到不同配置下的行为和质量变化。但是，合同影响模型输出不等于模型在声明效用下具有理性最佳响应；一个有限收益表满足均衡条件，也不能直接证明真实语言Agent达到相应均衡。相关理论需要与实际信息结构、执行行动和评价对象逐项对应[4-6]。
从应用角度，多智能体推荐还需要解决证据与偏好的区别。影片年份、类型等目录事实可以通过程序核查，用户是否喜欢一部影片则需要行为反馈或显式表达。某条引用存在，不代表它支持报告中的全部推论；多个Agent都赞成，也不能代替用户反馈。尤其在会话式推荐中，未来被推荐且标注为正的影片只是可观察目标，不是完整的真实满意度。上述区别直接影响实验标签、主指标和结论的解释。
综上，本课题围绕多智能体语义共识机制开展创新点研究，并以仓库中已有的影视搜索推荐系统作为应用载体。研究部分分析信息生产、证据交换、判断更新与集体决策之间的关系；系统部分实现请求接入、候选召回、多角色评审、确定性核验、共识排序及过程追踪。两部分相互衔接：研究为系统提供可执行机制，系统为机制提供真实目录、明确约束和可复现应用评测。

## 2. 研究内容
本课题以《博弈驱动的去中心化语义共识机制及在影视推荐中的应用》为总题目，研究内容包括多智能体语义共识机制研究，以及影视搜索推荐系统的设计与实现。前者是课题拟形成创新的主体，后者是已有代码仓库中的应用实现。影视召回、页面展示和常规接口开发属于系统工作，不能仅因使用了大语言模型或多个角色就作为独立算法创新。
!研究内容总体结构图|研究创新主线：信息生产与资源行动 → 带来源的报告 → 证据约束交互 → 集体决策；系统应用主线：请求接入 → 目录召回 → 多角色评审 → 约束门控 → Top-K与Trace。两条主线通过报告接口、执行器和核验结果连接。|5.3
### （1）研究内容一：博弈驱动的多智能体语义共识机制研究
研究内容一主要讨论：面对不完备、可能相互冲突的局部判断，如何让多个Agent通过可核验的信息交换和判断更新形成更可靠的集体决策，并在此基础上检验资源协调规则的必要性。该问题包含信息生产、交互更新和资源协调三个相连环节，三者服务于同一个研究目标，不分别扩大为三个已经完成的创新点。
前期已实现公开合同、不同资源行动、AEIC报告、信用结算与信誉更新，并完成通用问答实验。后续研究进一步检查信息互补能否转化为决策增量，拟采用带来源的主张、目标明确的核查和可执行状态更新，使审阅结果能够作用于最终决定。该部分目前已经形成原型、配对实验底座与开发结果，但新的交互规则及博弈协调贡献仍需要独立验证。
@@4
研究内容一的第一个环节是信息生产与报告表示。系统需要记录Agent采用了什么行动、访问了哪些输入，以及其判断依据是什么。AEIC接口分别组织Assumption、Evidence、Inference和Conclusion，即假设、证据、推断与结论。通过结构化报告可以建立统一的数据契约，并为解析、审计和实验复算提供条件。报告结构本身不作为事实正确性的保证，其有效性需要通过与自由文本、一般结构化报告及强单Agent方法的比较来检验。
第二个环节是证据约束的判断更新。针对一条可能错误的判断，系统应明确被核查的主张、引用来源、核查结果及更新范围。核查结果可以是接受、拒绝或未决；对于年份、类型等可确定事实，可以执行程序化检查；对于复杂文本和偏好解释，需要保留不确定性。拟研究的差异在于将核查结果与支持撤销、约束更新、候选重算等操作对应起来，使过程记录能够被实际执行，而非仅作为最终生成器可选择忽略的建议。
第三个环节是信息生产行动的协调。只有当不同查询、核验或分析行动存在可观察的互补与替代关系时，才有必要研究怎样分配预算。资源行动由执行网关计量，评价采用外部任务指标和实际成本。现有工作已实现有限收益表求解与相关检查，但其性质限于声明的经验模型。后续将与固定、随机、轮转及集中式控制器比较，检验协调规则是否具有额外价值，不将标准博弈公式直接列作本课题的新定理。
本课题拟重点形成的创新在于，把信息生产行动、带来源的语义判断和证据触发的状态更新连接为可执行的多智能体协作机制，并通过配对对照分析其决策收益。当前已有的正向结果属于前期整体配置的经验结果；新机制的创新性和有效性尚处于研究验证阶段。中期报告据此分别陈述已实现内容、已经取得的实验现象，以及下一阶段拟验证的研究假设。

### （2）研究内容二：影视搜索推荐系统的设计与实现
研究内容二基于本项目MAS仓库中的system目录开展。后端核心位于game_consensus_recsys包，前端位于frontend目录，实验机制通过适配层与系统连接。当前系统已经形成从结构化请求到候选检索、角色评审、约束核验、共识排序和审计输出的完整链路，可以通过本地演示、HTTP接口及前端页面运行。
!影视搜索推荐系统模块结构图|前端交互层：搜索输入、影片卡片、语音入口、轨迹面板；服务层：请求校验、HTTP适配、结果归档；执行层：Planner、Workflow、多Agent、ConsensusEngine；数据层：MovieLens目录、训练侧共现表、报告与Trace。|6.0
系统首先将自然语言查询及显式约束封装为SearchRequest，Planner使用请求时可见的信息生成执行计划。目录检索模块从MovieLens正式目录中召回影片，并可结合ReDial训练集影片共现关系补充候选。进入Agent评审前冻结短名单，各候选接受相同角色覆盖，避免部分候选因获得更多分析而得到不公平的排序优势。
多角色模块分别从偏好匹配、多样性和批判检查等角度形成候选级报告。约束验证器使用目录年份、类型和排除集合执行明确规则。共识引擎在硬约束通过后综合检索分数、Agent判断、证据状态及反对意见，输出Top-K结果，并保留尚未消解的异议。相关分数和权重属于现有工程配置，不作为已经学习得到的最优策略。

!系统总体请求处理流程图|SearchRequest → 请求校验 → 请求时规划 → 合同公开 → 目录召回 → 短名单冻结 → 并行Agent评审 → 覆盖检查与约束门控 → 共识排序 → SearchResponse及Trace归档。|7.0
系统向用户展示普通影视搜索推荐界面，同时提供可展开的机制审计视图。用户能够查看当前请求的执行计划、Agent行动、AEIC报告、候选排序分解、信誉变化和事件时间线。该设计使推荐结果与产生结果的过程相互对应，也为后续实验发现错误、定位降级及核查成本提供了入口。
系统采用同一模型客户端承载多个逻辑Agent，通过不同角色指令和独立上下文区分其职责。目录检索与明确硬约束检查由确定性程序执行。模型超时、空响应或结构错误进入失败处理和降级链路。报告将这种实现称为逻辑多Agent协作；当前仓库仍存在统一调度和排序程序，未实现跨机器无中心的P2P共识部署。
研究机制与系统实现之间保留清晰接口。前期系统接入公开合同和资源行动，能够记录真实的Prompt、预算及核验调用；最新证据更新实验仍位于独立实验包中，其离线验收不等于已经进入在线系统。后续工作将在开发实验支持具体更新规则后，再通过现有适配层接入系统，并重新完成回归与应用评测。

## 3. 关键技术
### 关键技术一：多智能体语义报告与信息生产过程建模
本课题首先将Agent的报告生产过程划分为输入观察、行动选择、资源执行、报告提交和结果结算。这样可以把最终文本与实际执行路径对应起来。若只在生成后给报告打分，无法证明评分规则影响了行动；因此，公开合同必须先于行动，合同内容和行动结果都应进入日志。
!公开合同与行动执行流程图|公开合同m → Agent读取任务与局部历史 → 声明行动 → 执行相应模型和资源路径 → 提交报告 → 验证与信用结算 → 更新信誉与下一状态。|5.5
合同包括信用规则、行动成本、信息可见范围和验证预算。行动集合包括低资源报告、完整结构化分析、追加验证及参考同伴。每类行动通过执行器映射到不同提示、最大输出Token、调用次数和可见输入。实验同时记录动作名称与实际消耗，防止把没有改变资源路径的标签当作投入变化。
在报告表示上，假设用于说明推理成立的前提；证据用于保存当前输入或工具能够支持的材料；推断解释从材料到判断的关系；结论给出任务要求的答案或候选立场。四个字段为空、缺失或格式异常时应保留原始响应和错误原因。格式修复只处理结构问题，不应替Agent补充事实或改变原结论。
@@8
AEIC的作用主要体现在统一接口。不同角色虽然承担不同职责，但可以通过相同数据模型记录其依据和结论。例如，偏好角色引用当前对话中的显式表达，影片核验角色引用目录年份和类型，批判角色指出某一推论所缺少的资料。系统可据此把一条异议定位到候选和证据，而不是只保留一段无法与程序对象对应的自然语言评论。
!AEIC报告与候选对象对应图|每份报告关联agent_id与candidate_id；A保存适用前提，E保存来源及引用，I保存推断，C保存支持、反对或未决。资源字段记录行动、Token和延迟；版本字段用于后续主张更新。|5.3
语义报告需要区分结构有效性、来源有效性与推论有效性。结构有效性判断字段和取值是否合法；来源有效性检查引用能否在允许输入中找到；推论有效性判断来源是否支持报告主张。前两项可以部分程序化，第三项通常需要任务核验器、独立标注或经过评估的代理判断。三类指标不能合并解释为同一种“正确率”。
前期实验还使用了证据新颖度、完整度和无依据翻转等信号。这些信号有助于观察模型行为，但词元增量并不等于语义新事实，完整字段也不保证证据正确。后续研究将以具体来源和原子主张为基本对象，减少由文本长度和格式差异带来的误解释。
@@9
### 关键技术二：证据约束的争议核查与状态更新
多Agent交互的关键是明确“哪一条判断因什么证据发生变化”。本课题把自然语言报告进一步组织为带编号的主张，记录主张所属实体、属性、适用范围、支持来源和候选影响。相同影片在不同年份的版本需要先做实体消歧；不同候选列表只表示排序分歧，不能直接视为事实冲突。
!主张定位与争议处理流程图|冻结初始主张 → 比较同实体同属性判断 → 检查硬约束风险及候选边界 → 选择需核查项 → 查询允许来源 → 输出接受、拒绝或未决 → 保存版本及决策影响。|5.8
争议选择优先考虑可能导致硬约束违反的事实，其次考虑可能改变Top-K入选边界的判断，最后处理只影响解释措辞的内容。没有有效争议时允许停止，不要求每例必须产生相同数量的反对意见。路由依据只能来自当前可见状态，不能按已知错误样本、电影身份或测试标签进行选择。
当前48例开发原型采用了定位主张后两次审阅的方案，但后续检查发现其规则尚不能严格识别成对冲突，审阅结果也没有成为强制状态转移。这些观察为新方案提供了明确改进目标。报告保留该原型作为阶段成果与失败分析，不将其直接称为已经有效的语义核验机制。
@@10
核验结果分为支持、反驳和证据不足三类。目录已经给出影片年份时，可直接检查其是否满足用户区间；目录没有演员信息时，不能用一条类型记录证明演员关联。对缺少资料的情况应标为未知。偏好解释则应与客观事实分开：某一解释缺少支持，不意味着用户一定不喜欢该影片。
!证据核验与更新状态转换图|已支持主张可因反驳证据撤销；未知主张可在新证据支持后确认；证据不足保持未决。每次更新都保存原主张、目标、证据、前后状态和理由；未经核验的多数意见不直接覆盖事实状态。|5.7
更新需要落实到程序中的候选状态。若已证实候选违反显式硬约束，则由约束模块排除该候选并保存规则；若某条支持被反驳，则撤销该条支持，并重算受影响分数；若仍未解决，则保留未知及其来源。对一条支持的否定不应删除无关证据，也不应无条件否定整个Agent的所有报告。
新的配对执行底座已把目标主张、证据引用、三态结果和理由作为核验接口。运行时合同检查与运行后语义评价分开，人工标签和未来推荐目标不能进入更新执行。受控事实错误与盲化模型代理评审可用于开发评价，人工审核条件具备后再补充独立金标准。当前仅完成离线工程验收，不能把合成案例通过率作为自然语义任务效果。

### 关键技术三：资源行动协调与博弈分析
资源协调研究以真实可执行行动为基础。Agent可以选择检索历史、查询协同信息、核查影片属性或停止，执行网关记录每次工具调用和模型消耗。需要协调的是这些行动怎样共同改变推荐决定，以及有限预算怎样分配；角色名称本身不构成利益差异，模型提示中的“奖励”也不自动形成真实经济主体。
!资源协调与决策评价关系图|当前状态与可执行行动 → 固定或学习的协调策略 → 实际工具与模型执行 → 统一决策器 → 外部任务结果及成本；训练侧估计行动价值，测试侧冻结策略并在执行后评分。|5.5
前期工作从公开信用规则出发，观察合同配置下的Follower行动变化。后续核查表明，部分高投入行动在声明的即时效用下并非最优响应，因此不能以动作变化证明一般激励相容。有限代理收益表上的势函数性质可以进行数值和代数检查，但该表需要覆盖实际行动，并与外部质量建立联系，才能讨论其在真实任务中的意义。
当前研究将博弈化协调放在信息互补和交互增量之后。首先检验真实行动是否存在互补，其次与普通集中控制器比较，最后才讨论有限策略菜单上的均衡和偏离收益。该顺序使理论对象与执行对象保持一致，也能避免在没有信息增量的报告池上继续调整支付规则。

### 关键技术四：目录约束下的候选检索与共识排序
影视系统以真实目录作为候选空间。每个影片具有稳定ID、片名、年份和类型，候选检索保留来源及检索分数。词法检索利用查询和元数据匹配，训练侧共现检索利用对话中影片关联。两类分数归一化后融合，其权重在开发集确定，再用于测试；测试目标不能被注入候选或用于调整权重。

### （三）信用结算、信誉与过程观察
前期机制以完整性、一致性、证据新颖度、已验证证据、有用纠正和无依据翻转等信号计算信用，再结合动作成本形成系统效用。信誉根据历史与本轮结果更新，用于后续影响力或过程观察。该设计把难以追踪的自由文本协作转为可以记录和复算的过程，但每个信号的语义必须按实际实现解释。
T信用与过程信号|信号|观察对象|解释限制
结构完整度|报告字段是否存在且合法|不能判断事实或推论正确。
一致性|声明与输出、报告内部或历史关系|一致不代表符合外部真值。
词元新颖度|相对可见文本的词元增量|不认证独立来源或语义新证据。

成本|调用、Token和记录延迟|旧成功日志可能不包含全部失败重试，需披露统计范围。
在后续审查中发现，旧合同部分高资源动作在声明的即时信用减成本下被低资源动作支配。因此，虽然模型会对公开条件作出行为变化，仍不能称其符合所声明效用的理性响应。这一检查直接限制了“激励相容”和“Stackelberg均衡”等表述，也说明需要将真实执行价值、信用函数与理论行动重新对应。
新的研究底座将来源、目标、状态与预算检查作为运行时合同，把语义支持和外部结果评价置于运行后。信用或评分的设计将服务于已经明确的任务目标，避免把字段完整率和自评满意度作为真实决策价值的替代。

### （六）证据更新机制的修订与配对执行底座

### （七）理论分析与阶段性创新定位
目前已实现有限矩阵求解器，可对给定损失矩阵求解原问题和对偶问题，计算最坏损失上下界、原对偶间隙以及双方单边改进空间。合成矩阵案例验证了确定性集合与随机混合策略的区别。数值证书只属于给定矩阵及其策略空间，若列仅包含有限几个候选输出，不能把受限游戏证书解释为整个推荐空间的最优保证。
前期还研究了有限代理收益表上的资源升级与差分信用。固定收益和有限策略菜单可以满足势函数或条件均衡性质，但保存的报告池中若没有能够纠正初始错误的新结果，选择器即便知道标签也无法制造额外正确答案。因此，“理论性质成立”与“真实任务有用”需要分别检验，不能拼接成同一成功结论。

### （三）请求时规划与工作流调度
ConsensusPlanner根据当前请求中可见的约束数量、类型偏好、查询长度、结果数量和时延预算计算复杂度，输出低、中、高风险计划。该实现是显式规则规划器，其作用是组织执行角色、拓扑名称和验证预算；尚不是经训练证明最优的动态路由策略。
T规划器的请求特征|特征|代码处理方式|作用

偏好类型|按数量增加复杂度并设置上限|识别存在偏好材料的请求。
较长查询|增加固定复杂度|作为组合意图的工程近似。

实际Workflow首先校验请求，再创建request_id和Trace；规划事件之后写入合同公开事件，随后执行检索和候选冻结。多个Agent通过线程池并行运行，返回结果按配置顺序重新整理，避免完成时间的随机顺序影响日志组织。报告进入共识前逐条校验，并生成候选覆盖检查事件。

### （六）确定性约束核验与共识排序模块
约束验证器负责检查明确的年份范围、必选与排除类型以及影片排除集合。在共识引擎中，只要验证器明确反对，候选就不进入最终决定。该设计把硬条件与软偏好分开：用户明确排除的类型不能靠高推荐效用抵消；缺少语义评审则保持中性，不解释为全体支持。
共识引擎先按候选归并报告，保存整轮信誉快照，对检索分进行归一化。语义部分用报告置信度和信誉权重合成支持与反对，证据部分计算已核验权重比例。排序综合检索分量、Agent效用、证据分量和反对惩罚，最后按分数与候选ID稳定排序，返回Top-K。

### （七）信誉更新与审计Trace模块
信誉在整轮候选评分后更新。共识引擎先冻结reputation_before，对本次所有候选使用同一权重，再汇总每个Agent的贡献并施加历史衰减。这样可避免先处理的候选改变后续候选权重，使候选输入顺序不会成为隐性影响因素。长期信誉的含义仍受核验信号质量约束，不能把内部累计量等同于真实用户信任。
Trace以request_id为主键，记录计划、合同、候选、Agent报告、覆盖状态、排序结果和前后信誉。HTTP服务在成功搜索后按请求归档，便于从页面结果追溯到具体候选和响应。归档不包含API密钥，错误消息也应避免暴露认证信息。
TTrace事件与审计用途|事件|记录内容|可检查的问题

public_contract_committed|机制名与合同先行动标记|公开规则是否在行动前出现。
shortlist_frozen|候选ID、数量与冻结策略|是否公平共享同一候选。
agent_completed|行动分布、报告数、Token与延迟|是否执行、资源是否重复统计。
coverage_checked|每候选角色覆盖、完整与一致标记|是否存在候选评审不均。
ranking_completed|选中影片和分数|最终结果能否与报告及门控对应。
Trace还记录agent_degraded事件，区分正常模型评审与确定性降级路径。完整审计的目的在于暴露实际执行，不把降级报告隐藏成正常模型推理。后续证据状态更新接入时，将在该结构上补充主张版本、核查目标及更新前后影响。

### （八）服务接口与异常处理
系统提供基于Python标准库的HTTP服务，同时保留FastAPI适配。health接口用于服务状态检查，search接口接受结构化查询并返回SearchResponse。前端及移动入口通过适配逻辑取得媒体卡片与紧凑Trace，核心排序和约束规则仍由统一Workflow执行，避免不同入口产生不一致的业务行为。
模型客户端负责请求配置、结构解析与错误转换。超时、空JSON或非法结构可能触发重试或降级，相关过程进入日志。没有外部模型条件时可以运行确定性演示，用于检查目录、约束和审计链；这种离线路径不作为真实模型能力结果。
T异常情况与处理方式|情况|系统处理|报告与验证要求
