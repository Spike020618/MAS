# 中期汇报：系统证据、优化与演示用例计划

## 一、当前判断

当前影视推荐系统已经具备可运行主链路：请求规划、目录检索、多角色报告、证据/信誉聚合、Top-K 输出、trace 与异常降级。但它暂时不适合直接作为答辩截图，原因不是功能缺失，而是论文机制在应用层的呈现还不充分。

### 必须先修的机制一致性问题（P0）

1. `ContractualDeepSeekReviewAgent` 会先选择行动，但随后所有行动仍进入同一个 `DeepSeekReviewAgent.review` 生成路径。需要让 `low_effort / aeic_effort / verify / defer_imitate` 真正对应不同 Prompt、调用次数、Token 上限和可用信息。
2. 当前系统只有单轮并行审议；如果将其描述为论文三轮协议的完整实现会过强。可选择：
   - 实现两至三轮、同轮隔离和上一轮可见历史；或
   - 明确标为“单轮应用切片”，只验证公开合同、行动执行和可审计聚合。
3. README 仍称 `M0 + M1 skeleton`、静态基线，和当前对外叙事不一致，需要按照真实完成状态更新。

### 必须先修的演示质量问题（P0）

1. 默认处理后 MovieLens 目录尚未生成，系统回退到 8 部内置电影；应先构建正式目录并显示目录规模与来源。
2. 当前多个候选的共识分数均为 `1.0`，缺少区分度；需要重新标定 retrieval、support、oppose 和 evidence 权重，并在界面中显示分项而非只有总分。
3. 当前确定性检索已经过滤全部硬约束，Verifier 很少有机会展示否决；应保留“召回候选”和“硬约束过滤后候选”两个阶段，显式呈现被拒绝项及原因。
4. 页面标题中的“去中心化”与实际 Planner / Consensus Controller 架构不符，应改为“机制驱动的多智能体影视推荐”。

## 二、答辩系统页面应该展示什么

不要只截最终推荐卡片，也不要把大段 JSON 当主要证据。建议形成 5 张工作图片。

1. **请求与执行计划**
   - 用户自然语言请求、硬约束、偏好和 Top-K。
   - Planner 选择的风险等级、Agent 角色、验证预算、信息策略。
   - 公开合同摘要与时间戳。

2. **候选召回与约束过滤**
   - 召回候选、来源、检索得分和目录证据。
   - 被硬约束拒绝的候选及具体原因。
   - 进入多 Agent 审议的候选集合。

3. **多 Agent AEIC 工作台**
   - Preference / Diversity / Critic 三个角色并列。
   - 每个角色显示行动徽标、A/E/I/C 摘要、Token、延迟和置信度。
   - 至少存在一个支持、一个反对或弃权，能够看到真实分歧。

4. **候选级共识审计**
   - 每个候选的 retrieval、decision consensus、evidence consensus、dissent penalty 分项。
   - 接受证据、残余异议、贡献 Agent 和最终排序理由。

5. **失败与降级路径**
   - 模拟一个 DeepSeek 超时或非法 JSON。
   - 显示 agent degraded、确定性 Agent 继续、最终仍返回安全结果。
   - 强调失败被记录，而不是隐藏。

## 三、推荐演示用例

### Case A：硬约束 + 思想性（主案例）

> 推荐 2010 年以后的思想性科幻剧情片，不要动作片和灾难片，给出 3 部，并说明每部的证据与争议。

期望展示：高风险规划、年份/类型硬约束、Preference 与 Critic 的不同关注点、`降临 / 星际穿越 / 银翼杀手2049` 等候选之间的解释差异。

### Case B：结果不足时拒绝凑数（安全案例）

> 推荐适合亲子一起看的温暖科幻动画，不要灾难和暴力内容，最多 3 部。

期望展示：如果只有《机器人总动员》满足条件，系统应返回 1 部并说明候选不足，而不是用《疯狂的麦克斯》或《降临》填满 Top-3。该案例可以突出硬约束不可被偏好分数补偿。

### Case C：相关性与多样性的冲突（多 Agent 案例）

> 想看节奏紧张的科幻悬疑片，但不要三部都来自同一种叙事风格；兼顾思想性和类型多样性。

期望展示：Preference 倾向高相关候选，Diversity 反对同质化列表，Critic 质疑“节奏紧张”等缺少目录证据的推断，最终 Top-K 保留异议。

### Case D：单一候选而非错误扩充（边界案例）

> 推荐 1990—1999 年的中国历史剧情经典，最多 3 部。

期望展示：目录只有一个可靠候选时返回一个，并显式报告覆盖不足。用于证明系统不会为了满足数量而放松硬约束。

### Case E：API 降级（工程案例）

> 使用 Case A，但人为触发 Critic Agent 超时。

期望展示：trace 出现 `agent_degraded`，确定性检索、偏好与约束验证继续工作，响应中标注审议不完整和可信度下降。

## 四、优化顺序

1. P0：行动真正控制资源路径；明确单轮或实现多轮。
2. P0：构建正式 MovieLens 目录；修正结果饱和和硬约束阶段展示。
3. P1：重构前端为 5 个证据视图，而不是“结果卡片 + 原始 JSON”。
4. P1：加入固定演示模式，保存 Case A–E 的输入和可复现 trace。
5. P2：完成 ReDial / MovieLens 离线评测，输出 Hit@K、Recall@K、NDCG@K、约束满足率、证据支持率、Token 和 P95 延迟。

## 五、HTML 中期汇报的使用方式

- 论文部分使用正式论文图和冻结实验结果。
- 系统部分使用系统架构图加 3 张核心工作截图：请求/计划、多 Agent 工作台、共识审计。
- 失败降级截图放在备份页或答辩问答中。
- MovieLens/ReDial 指标未完成前，不在主页面写未经验证的系统性能数字；只写“主链路可运行”和已验证的工程能力。
