## 1. 审计问题（针对当前版本）

对每个案例回答三问，归入唯一主因：

- **Q1 初始决策本来就对吗？** 对 → 维持是正确行为，"零更新"不是缺陷，成功指标应改为正确维持率与误改率。
- **Q2 允许的资料/候选池里存在更好输出的机会吗？** 不存在 → 任何修改都只是波动；瓶颈在信息获取/候选供给，改核查接口无用。
- **Q3 机会明确存在时为什么没落实？** 细分：没读懂证据 / 核查目标与决策无关联 / 动作范围不足 / 合同拒绝。只有这一类直接支持修改核查接口。

**预登记判定规则**：只有 Q3 为主导原因时才修改核查接口；Q1 主导 → 重定义成功指标与 gate；Q2 主导 → 改信息获取与诊断设计（如人工注入已确认机会的小批）。三个分支都不允许"加强 prompt 要求必须修改"。

## 3. Phase A：probe 小批全三问审计（离线，0 API）

工具 `experiments/audits/audit_decision_linked.py`（只读封存数据；标签走 `labels_for` 封存后路径）。每例产出：

- **Q1**：`quality(initial_decision, gold)`（QA 精确匹配；rec Top10 命中率），初始对/错直接落判。
- **Q2 机械层**：QA——指派证据与问题/关键前提的词面覆盖（重叠仅作代理，不是语义认证）；rec——gold target 是否在候选池、是否在 Top10 之外（gold 已在 Top10 → 无换入机会；不在候选池 → 无机会）。
- **Q3**：linked 臂 `decision_effect`（choice=keep/revise、reason）逐条记录并与 Q1/Q2 对照；ordinary 臂输出与 patch；revise 未被接受的具体合同拒绝原因；keep 的理由是否与机会矛盾。
- **Q2 语义裁决**（资料是否真正支持更好答案）：4 例在报告中给出材料摘录 + gold + 当前决策，由**用户人工裁决**；或账户恢复后以小额模型判（≤8 次请求、硬上限 0.1 元、用户执行）。审计本身不代做语义判断、不冒充语义认证。
- 产出：逐例 JSON + 报告 + 三问主导分类（每例一个主因 + 证据行）。

## 4. Phase B：主批 399 例执行侧无标签审计（离线，0 API）

落实 update_repair 计划第 1 步，对 693 条有效 game 核查逐条分类：

- **无修改依据**：核查目标（target claim）与决策关键前提无桥梁（机械代理：claim 文本与问题/决策词面重叠；不重叠/低重叠计为代理性"不相关"）。
- **无决策桥梁**：反驳触及关键前提但未给 patch（旧接口无 keep/revise 声明，无法区分"认为不该改"与"没有建立连接"）。
- **合同拒绝**：10 例（已审：全部 same_decision + 未用指派证据）。
- **同值修改**：同上 10 例。
- 705 条空补丁按 verdict/rationale 分布聚合；分层抽 30 例输出原文摘录，供账户恢复后的语义判读（用户或小额模型）。
- 边界：无标签，不判机会是否存在，只判"若有机会，执行链路断在哪一环"。

## 6. Gate 与成功指标重定义（依审计分支，审计后一次改定）

- Q1 主导：gate 改为"正确维持率 + 误改率"（如：维持正确 ≥ 参照且误改 ≤ 阈值），`improved>0` 不再是必要条件。
- Q2 主导：小批先做"机会注入"验证（人工确认存在可改进案例与指派支持材料），再测执行链路；否则任何执行指标都无解释力。
- Q3 主导：保留 `improved>0` gate（此时才合理），并按具体失败模式（读懂/目标/范围/合同）定向修接口。
- 重定义落地前，`repaired_release.py` 的阻断保持不变。
