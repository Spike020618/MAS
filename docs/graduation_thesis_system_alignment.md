# 毕业设计研究—系统对齐方案

> 版本：2026-08-12（已由新方案取代）  
> 目标：将现有 MAS 研究成果、开题报告与 `tvos-agent` 系统收束为“两个研究点 + 一个系统”，并明确哪些内容保留、降级或重构。

> **修订说明**：经进一步确认，毕业论文不更换叙事主线。博弈与多智能体语义共识仍是核心，影视搜推仅作为验证场景，`tvos-agent` 仅作参考。后续以 `docs/game_consensus_search_recommendation_system_design.md` 为准。

## 1. 结论先行

建议将毕业论文总题目从过度强调“去中心化语义共识”，调整为：

**面向对话式影视搜索推荐的可信多智能体协作与自适应生成式检索研究**

如必须尽量贴近原开题题目，可使用：

**博弈驱动的可信多智能体语义共识机制及在影视搜索推荐中的应用**

整篇毕业设计收束为：

1. **研究点一：面向策略性行为的可信多智能体审议机制。** 研究 Agent 在从众、低努力、复制、无依据翻转等行为下，如何通过 AEIC 可观测报告、验证反馈、信誉激励与自适应机制获得可靠且成本可控的集体判断。
2. **研究点二：面向生成式搜推的风险—成本自适应协同检索机制。** 研究生成式召回、传统检索、补充检索、审议验证与降级链路如何根据查询复杂度、候选分歧、证据质量、历史信誉和时延预算动态编排。
3. **系统：可信对话式影视搜索推荐系统。** 以 Plan Agent + DAG Workflow 为执行骨架，承载传统影视检索、MovieSID 生成式候选、向量补召、AEIC 多 Agent 审议、验证重排、流式回答、缓存和降级，并提供完整可观测性。

这三个部分不是并列拼盘。研究点一解决“多个 Agent 的报告是否值得信”；研究点二解决“什么时候应调用哪些搜推与协作链路”；系统提供真实影视场景中的统一验证载体。

## 2. 为什么要调整原开题叙事

原开题已经给出三个创新点：去中心化语义共识、演化博弈收敛、动态验证成本优化。但现阶段实际成果已经发生明显演进：

- MAS 已经形成 AEIC 结构化报告、IC/EC/EQ/EV 信号、信誉/激励、Stackelberg 机制、通信拓扑、自适应路由以及成本—质量实验资产。
- 最新研究计划已意识到：仅在生成后对信号做加权不能证明真实的 Stackelberg follower response；必须让 Agent 在调用前看到机制，并真实选择努力、验证、模仿或延迟报告等行动。
- 现有论文结果还发现了从众、负向棘轮、方差坍缩和模型相关吸引子。这些成果比原开题中抽象的“自然语言语义收敛”更具体、更可测、更有论文价值。
- 组内搜推方向强调 Plan Agent + DAG、生成式 SID 召回、传统 TIS/向量补召、缓存、超时降级和 LLM Ops。这为第二研究点和系统提供了很好的工程问题，但不能原样照搬为你的学术创新。

因此需要做两处降调：

1. **不再把“完全去中心化”作为系统硬承诺。** 对话式 AI 搜系统天然存在 Planner、Workflow 和 Merger。论文可以研究局部 peer-to-peer 审议和弱中心聚合，但不应把中心化 DAG 系统描述成完全去中心化。
2. **不把 SID 模型训练本身作为个人研究创新。** 在没有完整工业码本、训练数据、模型部署和线上 A/B 条件时，它更适合作为候选生成组件。你的创新应落在可复现实验的协同、验证、路由与降级机制上。

## 3. 研究点一：可信多智能体审议机制

### 3.1 核心问题

在 Agent 存在有限理性、努力成本、从众或策略性报告时，如何利用结构化语义报告、局部验证和激励机制，提高集体判断可靠性，同时保留信息多样性并控制成本？

### 3.2 方法定义

建议统一使用 **AEIC-MD** 作为方法名：

- **AEIC 报告接口**：Assumption、Evidence、Inference、Conclusion；
- **行为测量**：证据新颖度、复制率、无依据翻转、推理—结论连续性、报告完整度；
- **可信信号**：IC/EC/EQ/EV、验证结果、跨轮行为和历史信誉；
- **机制动作**：低努力、完整 AEIC、追加验证、参考/模仿、延迟决定；
- **机制控制**：信用分配、验证预算、反馈可见性、通信结构与停止条件；
- **动态响应**：Agent 事先看到规则并做真实行动选择，机制根据跨任务行为更新信誉和后续影响力。

### 3.3 可主张的创新

1. 将自由文本中的从众、复制和无依据立场翻转转化为可计算的 AEIC 局部行为指标。
2. 设计可见的信用—验证契约，使 Agent 的努力、验证和报告策略产生真实 follower response，而非生成后的虚拟收益计算。
3. 在决策质量、行为健康、信息多样性和调用成本之间进行联合优化，并刻画静态机制与动态机制的适用边界。

### 3.4 与现有成果的关系

- 现有 QA、评审面板、拓扑和路由结果可以作为前期研究与基线。
- 已有静态 AEIC + Stackelberg 权重继续保留，但表述为静态聚合基线。
- 新的正式实验应以 `docs/research_execution_plan.md` 中 E1–E6 为主，尤其补齐真实 follower response。

## 4. 研究点二：风险—成本自适应的生成式搜推协同

### 4.1 核心问题

生成式推荐能直接产生候选并改善语义理解，但存在幻觉候选、供给不可用、重复、偏好过拟合、时延和不可解释等风险；传统检索稳定、可验证，但处理复杂意图和组合约束的能力有限。研究点二回答：

**对于不同查询与中间状态，何时直接检索，何时使用生成式候选，何时补召、验证、多 Agent 审议或降级，才能在效果、可靠性与成本之间取得更优权衡？**

### 4.2 系统内的 MovieSID 生成式链路

不训练工业级自回归推荐大模型，而是在影视域构建可控、可复现的 MovieSID 原型：

1. 为本地电影条目分配稳定 `movie_sid`；
2. 将用户画像、会话偏好和行为序列编码为推荐上下文；
3. 让 LLM 在受约束的 SID 词表或候选前缀树中生成 `topic + movie_sid`；
4. 将 SID 映射回电影实体并做存在性、可播放性、黑名单和会话去重校验；
5. 对 topic/SID 表征做向量补召，弥补生成结果过少或过窄；
6. 与关键词/字段检索候选合并，进入验证、重排和解释生成。

该原型用于研究链路，而不是声称复现工业 SID 训练体系。

### 4.3 自适应编排状态与动作

Planner 只使用在线可见信号：

- 查询意图、复杂度与约束数量；
- 用户画像/会话上下文完整度；
- 传统检索命中数量与分数间隔；
- 生成式候选合法率、重复率、供给覆盖率；
- 两路候选的 overlap、rank disagreement 和证据冲突；
- Agent 历史信誉、验证风险、剩余时延与 token 预算；
- 缓存是否命中及结果新鲜度。

可选动作：

- `lexical_retrieve`：关键词、演员、导演、类型、年份等字段检索；
- `generative_sid_retrieve`：生成 topic + MovieSID；
- `vector_supplement`：基于 topic/SID/用户表示补召；
- `targeted_review`：只对冲突候选或高风险断言进行 Agent 评审；
- `full_deliberation`：复杂、高风险且预算允许时执行 AEIC 多 Agent 审议；
- `verify_and_rerank`：实体、供给、证据与解释一致性验证；
- `fallback`：超时或模型失败时返回缓存/传统检索结果；
- `stop_and_stream`：候选充分且风险低时提前输出首 token。

### 4.4 可主张的创新

1. 将多智能体“分歧与证据质量”从最终聚合信号扩展为生成式搜推工作流的在线路由状态。
2. 提出同时考虑质量、候选有效性、行为风险、时延和 token 成本的动态工作流策略。
3. 通过选择性审议与选择性验证避免每次请求都运行昂贵的多 Agent 链路，并用显式降级保证最坏情况下的可用性。

### 4.5 实验设计

至少比较：

1. 仅传统检索；
2. 仅生成式 MovieSID；
3. 固定“生成 + 传统 + 向量”融合；
4. 固定全量多 Agent 验证；
5. 规则路由；
6. 学习型自适应路由；
7. Oracle 上界。

主要指标：

- 检索/推荐：Recall@K、NDCG@K、约束满足率、候选有效率、去重后覆盖、列表多样性；
- 回答可靠性：无供给推荐率、实体幻觉率、理由—候选一致率、证据支持率；
- 行为过程：Agent 分歧、证据新颖度、无依据翻转、少数有效候选保留率；
- 工程性能：首 token 延迟、端到端 P50/P95、模型调用数、token、缓存命中率、降级成功率；
- 综合目标：质量非劣约束下的成本/延迟下降，或固定预算下的可靠性提升。

## 5. 一个系统：可信对话式影视搜索推荐平台

### 5.1 目标架构

```text
Web / TV / Voice / Image Client
             |
      Streaming Gateway (SSE/WebSocket)
             |
      Session + Context Manager
             |
          Plan Agent
             |
      Typed DAG Workflow Engine
       /        |          \
Traditional  MovieSID    Profile/Memory
 Retrieval   Generation   Retrieval
       \        |          /
        Candidate Merger
              |
   Risk & Disagreement Estimator
       /                    \
 cheap verify        AEIC-MD deliberation
       \                    /
       Evidence-aware Reranker
              |
      Answer/Card Generator
              |
       Quality/Safety Gate
              |
   Stream result + trace + metrics

Fallback plane: query cache -> session cache -> traditional retrieval -> safe empty result
```

### 5.2 工程分层

参考组内四层治理思想，但用适合本项目的命名：

- `util`：schema、日志、计时、缓存键、安全、序列化；
- `service`：LLM、embedding、catalog、profile、cache、verifier 客户端；
- `op`：意图识别、查询拆解、各类召回、合并、过滤、去重、重排、验证、生成；
- `graph`：简单搜索、复杂搜索、个性化推荐、图片搜、失败降级等 DAG。

研究代码与系统代码通过稳定接口连接：MAS 输出机制状态、信誉、路由动作和审议结果；系统不直接复制实验脚本。

### 5.3 必须支持的可观测性

每次请求保存：

- `request_id/session_id/user_id_hash`；
- query、意图、上下文版本和隐私处理结果；
- DAG 计划、节点状态、并行关系、重试和停止原因；
- 每路候选、分数、来源、过滤/去重原因；
- 每个 Agent 的 AEIC、可见信息、信誉和机制动作；
- 验证证据、冲突位置和最终采纳理由；
- 首 token、总时延、token、调用数、缓存命中和降级路径；
- prompt、模型、数据、策略和 schema 版本。

前端 Debug 模式应能展示内部 trace；普通用户模式只显示推荐卡、简洁理由和必要来源。

## 6. `tvos-agent` 现状判断

现有系统可以保留为交互壳和数据原型，但后端核心需要重构。

### 6.1 可保留

- React 前端、搜索框、语音、图片上传和 WebSocket 交互入口；
- Django API 外壳；
- 豆瓣影视数据与 MCP 搜索工具中的字段/倒排检索原型；
- 基础媒体卡片和本地播放能力；
- Redis、日志和启动脚本的思路。

### 6.2 当前关键缺口

- `service/core.py` 主要让 LLM 直接“编”出 5–8 部电影，事实候选没有以检索供给为约束，容易产生实体和属性幻觉；
- `task.py` 明确删除了规划器，只剩敏感词过滤，和 Plan Agent + DAG 目标相反；
- LangChain/MCP 工具与主搜索链路基本割裂，存在“有工具定义但主请求绕过工具”的两套路径；
- 没有用户画像、短期/长期记忆、行为序列或 session topic 去重；
- 没有生成式 SID、向量补召、候选融合、证据重排和供给校验；
- 没有多 Agent 审议、AEIC、信誉、验证预算或自适应路由；
- 缓存、超时、熔断、降级、请求级 trace、评测与实验版本管理不足；
- 当前流式能力主要是结果广播，并非 Planner/DAG 节点与回答 token 的可观测流式执行。

### 6.3 重构原则

不要继续在 `Service` 大类里增加 prompt。应将现有代码冻结为 `legacy` 参考，实现新的 typed pipeline；待新链路通过回归测试后再切换 API 入口。

## 7. 分阶段实施路线

### P0：冻结论文边界与基线（1 周）

- 确认论文总题目、两个 RQ 和每个研究点的主指标；
- 冻结 MAS 已有结果的角色：正式结果、前期结果、静态基线或废弃路线；
- 为 `tvos-agent` 建立现状架构图、API 清单和最小回归样例；
- 明确系统演示不等于论文实验，二者共享组件和日志，但使用独立数据划分。

### P1：系统骨架与传统检索基线（2–3 周）

- 定义请求、候选、证据、计划节点、Agent 报告和 trace schema；
- 实现 Context Manager、DAG executor、超时/重试/并行和 SSE；
- 将 MCP 豆瓣检索接入主链路，完成字段检索、过滤、去重、重排；
- 建立离线 query—relevance 小型评测集和一键回归测试。

### P2：MovieSID 与融合检索（2–3 周）

- 构建 MovieSID 词表、实体映射和约束生成；
- 接入向量补召与 topic 化；
- 实现传统/生成/向量三路候选归一化、融合与供给校验；
- 完成仅传统、仅生成、固定融合三组基线。

### P3：接入 AEIC-MD（2–3 周）

- 将 MAS 的 schema、行为指标、信誉和机制控制器封装成系统服务；
- 对高分歧或高风险请求执行 targeted review/full deliberation；
- 将验证结果反馈到重排与解释，而不是只生成一段共识文本；
- 前端 Debug 面板展示 DAG、候选来源、AEIC 冲突和降级路径。

### P4：自适应路由实验（3–4 周）

- 先实现规则路由，再训练轻量学习路由；
- 严禁使用 ground truth 或事后收益作为在线特征；
- 完成固定链路、规则路由、学习路由和 Oracle 对比；
- 报告质量非劣、成本、首 token/P95 和最坏组性能。

### P5：论文与系统收口（2–3 周）

- 系统演示准备简单检索、复杂约束推荐、个性化多轮、模型失败降级四条脚本；
- 论文分别报告研究点一的机制实验、研究点二的搜推路由实验；
- 用系统案例展示两者如何共同工作，但不拿少量演示案例替代正式统计实验。

## 8. 应立即停止或避免的工作

- 不再新增只改变 prompt 文案、却没有行为操纵或可检验假设的“Agent 创新”；
- 不再把静态生成后加权称为真实 Stackelberg 博弈响应；
- 不再让 LLM 无供给约束地直接生成电影事实并作为推荐结果；
- 不从零复刻工业 TPP、Whale、TIS 或大规模 SID 训练平台；
- 不为了“多智能体”而每个请求固定调用多个模型；
- 不把前端动态效果、语音或图搜单独包装成研究点；
- 不同时维护 Swarm、LangChain、Hermes 等多个主框架。核心应该是自有 typed DAG，框架只作为可替换实现依赖。

## 9. 最终答辩叙事

一句话版本：

> 本文面向对话式影视搜索推荐，首先研究如何通过 AEIC 结构化报告、验证反馈与博弈激励识别并抑制多智能体中的从众和低质量策略行为；进一步研究如何将这些可信信号用于生成式召回、传统检索和多智能体审议的动态编排，在保证推荐质量与可靠性的同时降低模型调用和响应时延；最终在一个支持 MovieSID 生成式候选、混合检索、流式 DAG、验证重排和降级兜底的影视搜索推荐系统中完成验证。

这个叙事能同时解释：为什么需要多智能体研究、为什么系统是影视搜推、为什么组内生成式推荐材料相关、以及为什么 MAS 已有成果没有被推倒重来。
