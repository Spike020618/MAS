一、研究内容简介
1. 选题背景
REST （ Representational State Transfer， 表 述 性 状 态 转 移 ） 是 一 种 软 件 架 构 风 格 ， 由 Roy Thomas
Fielding 博士在 2000 年提出。它定义了一种网络系统之间通信的设计原则，尤其适用于 Web 服务，其核
心思想是将网络中的信息资源进行抽象，通过统一接口对资源进行操作[1]。REST 基于 HTTP 协议，能够
有效地管理和传输网络资源，并提供一种简洁和通用的资源访问方式，它使用 HTTP 协议中的方法（如
GET、POST、PUT、DELETE）来操作资源，且要求无状态通信，使每个请求都包含必要信息。REST 架
构具有简单、高效、灵活和可扩展的特点，已广泛应用于 API 设计、Web 服务和分布式系统。
接口一致性测试是验证系统各组件间交互是否正确的测试，主要检查系统与外部或内部模块之间的
数据交换是否符合预期。它通过测试接口的请求和响应，确保系统接口的功能、可靠性、性能和安全
性，以保证接口在不同场景下都能正常工作。自动化测试的通用流程包括：预处理、测试用例生成、测
试用例执行和测试结果评判等四大部分。其中，测试结果的评判在接口测试中至关重要，它直接影响对
接口质量的判断。测试结果评判的核心在于对比实际输出和预期输出，评估系统是否满足功能、性能、
安全等预定要求。自动化评判的准确性决定了测试过程的高效性，但目前的研究多集中于测试用例生
成，导致自动化测试结果评判在复杂场景中仍然存在局限性。
测试结果的评判主要包括两方面的内容：语法层面的评判和语义层面的评判[2]。语法层面的评判可
以通过 REST 接口文件的定义使用工具实现，确保测试结果的响应结构和字段类型符合规范，然而，语
义层面的评判更加复杂，涉及判断数据内容是否符合业务逻辑和实际需求，这部分传统上主要依赖于人
工判断，测试人员通过对比实际结果和预期结果，逐项确认是否符合测试要求。这种方法通常耗时较
长，且容易受到人为因素影响，导致判断结果不一致。此外，随着系统复杂性和接口数量的增加，人工
评判的效率难以满足需求，尤其在大规模接口测试中，人工判断更容易出现遗漏和误判。如果能够设计
一种测试结果语义评判规则的形式化描述，就可以从语义约束层面自动地判断测试结果是否符合业务逻
辑和预期需求。这种形式化的规则描述能够将人工判断转化为标准化的规则，通过程序化的方式进行自
动评判，从而显著提高测试结果评判的效率和准确性。
虽然有大量关于测试用例生成的研究，但对测试结果的评判却很少被涵盖。对测试用例的测试结果
的研究通常被定义为“测试预言” （Test Oracle）问题，Weyuker 是早期的贡献者，他在 1982 年观察到“尽
管许多测试文献描述了基于测试预言的理论和实际可用性的方法，但在许多情况下，这样的测试预言实
际上是无法实现的”。

共同进化算法，探索可能的断言空间，以减少假阳性和假阴性，从而优化测试预言的准确性。Tufano 等

其他基于机器学习的研究也逐渐兴起。Valueian 等人[9]基于测试输入和测试结果，使用人工神经网络

对于基于断言或静态规则的简单预言，可能只检查结果是否符合特定条件，语义覆盖较浅；对于基
于模型、NLP 或机器学习生成的复杂预言，可以更深入地考虑语义，但通常难以确保全面覆盖，并且基
于机器学习和深度学习的方法缺乏相关的数据集，这些方法多基于单元测试生成断言或测试预言，关注
的是局部行为，缺乏对 REST 接口整体测试结果的评估能力和语义一致性方面的深入考量[17]。
此外，还有一些相关的测试工具研究，Zheng 等人[18]提出了一个名为 RESTLess 的 REST API 模糊
测试增强方法，通过结合 LLM 的语义优化和基于参数权重的渲染顺序优化，有效提高了测试序列的语义
质量和长度，从而增强了漏洞检测能力。Golmohammadi[19]研究了如何利用基于搜索的软件测试方法，
特别是 EVOMASTER 工具，来提高 RESTful API 的白盒测试效率。Kim 等人[20]提出了 RESTGPT，一种
利用大型语言模型 (LLM) 提取机器可解释的规则和生成示例参数值来增强 REST API 测试的方法，这些
方法主要关注的测试的过程而非测试结果的评判。
对于一些自动化的测试工具，国外的研究主要集中在自动化工具的开发，如 Postman、SoapUI 等
[21]，这些工具能够自动生成和执行测试用例，但在结果评判方面仍依赖人工手动定义评判规则。国内研
究则以开源测试框架（如 JMeter、HttpRunner 等）为主，关注如何提升测试的覆盖率和结果判定的自动
化程度。这类框架提供了基本的测试执行和响应码校验功能，但对复杂数据的关联关系和逻辑评判支持
有限[22]。
TTCN（Testing and Test Control Notation，测试与测试控制表示法）是一种国际标准化的测试语言，
专门用于描述和执行各类系统的测试。其最新版本为 TTCN-3，TTCN-3（Testing and Test Control Notation
Version 3）是一种灵活、强大且与平台无关的测试语言，适用于黑盒测试。在 TTCN-3 中通过将接收到的
实际结果与预定义的期望“模板”进行匹配来得到测试结果的评判结果，但模板只关心它正在匹配的这一个
独立的消息，无法洞悉测试的上下文，无法定义复杂的语义关联关系，需要额外自定义函数来弥补其在
语义验证上的短板。
综上，本课题的研究意义在于自动化评判 REST 接口一致性测试的结果。首先提出一套 REST 接口一
致性测试结果的自动化评判流程，旨在通过标准化步骤自动化地对测试结果进行评估。其次，提出 REST
接口一致性测试结果语义评判规则的形式化定义，通过形式化定义准确简洁地描述评判规则，从而保证
测试结果在语法和语义层面的一致性和正确性。最后，对输入文件到输出评判结果之间的映射规则进行
了形式化定义，并引入基于状态扩展的下推自动机模型作为核心验证机制，用于处理复杂的状态转换和
数据依赖关系。本课题将实现 REST 测试结果的自动化评判，无需人工介入，通过自动化的评判机制大
幅提高测试效率、准确性和一致性，减少人为错误的可能性。

（1）研究内容一：基于有向图扩展下推自动机的 REST 接口一致性测试结果语义评判方法
此研究内容的主要目的在于提出面向语义的 REST 接口一致性测试结果评判的关键技术。首先本课
题提出了一套面向语义的 REST 接口一致性测试结果评判流程，以此指导面向语义的测试结果的评判。
该流程在语法检查的基础上加入了语义检查，从而更加全面地评估测试结果的准确性与一致性，流程中
定义需要的输入条件以及从输入到输出之间的映射流程。
评判流程有 3 个输入，分别是符合 openAPI3.0 规范的 REST 接口文件、测试结果语义评判规则文件
和需要评判的测试结果文件，主要包括前期准备、文件解析、测试结果分组、语法检查以及语义检查等
步骤。
其次，本课题提出测试结果语义评判规则的形式化定义，通过形式化定义，能够准确且简洁地描述
出测试结果的语义，根据测试结果语义完善评判规则从而实现更加准确的评判。测试结果语义评判规则
主要包含了两个方面：响应码规则和数据语义规则
响应码规则通过验证测试响应之间的依赖关系是否成立来判定返回响应码是否符合预期。依赖关系
指的是各个测试响应之间的依赖关系，如果将每一个接口视作一个单元，依赖关系可以是方法间（单元
内部）和接口间（单元之间）的依赖关系。其核心在于明确哪些方法或接口的执行结果可能影响其他方
法或接口的行为。通常情况下，这种依赖关系会影响测试用例的执行顺序，以及后续接口返回的预期响
应码。
方法间依赖关系指的是同一个接口内部的不同方法之间的依赖关系。例如，某个接口的 GET 请求可
能依赖于前面执行的 POST 请求的结果，GET 请求的返回结果可能需要 POST 请求成功并返回一定的数
据才能正确执行。接口间依赖关系指的是不同接口之间的依赖关系。在接口测试中，某些接口的执行结
果可能会影响其他接口的行为。
数据语义规则主要关注返回数据的合法性以及符合业务逻辑的要求。即使响应码正确，返回的数据
内容仍然需要符合特定的数据语义。数据语义规则包括字段值语义规则和数据关联关系语义规则。字段
值规则用于主要描述测试响应的响应体中各字段自身的语义，主要包括格式要求、范围要求以及枚举值
要求等。
数据关联关系语义规则主要描述了内部关系和蜕变关系，内部关系描述测试结果内部，响应体中字
段之间的关联关系，主要包括线性关系、多元方程组关系、简单函数关系、集合关系、条件依赖关系和

最后，在测试结果评判阶段，对从测试响应到评判结果的映射规则进行定义，以此来指导面向语义

关键技术二：测试结果语义评判规则的形式化定义
在评判测试结果是否通过时，仅依赖语法检查可能会导致误判。例如，在一个 GET 请求中，返回了
200 状态码和响应数据，从语法角度来看，这表面上似乎是一个有效的响应。然而，从测试结果判定逻辑
的角度看，这可能并非预期的结果。若该请求依赖于某个前置操作（如 POST 请求）的成功执行，但前
置操作未成功或资源状态未准备好，则即使 GET 请求返回了 200 和有效数据，这种响应也不应被视为正
确的结果。此外，对于测试结果来说，尤其是对于 GET 请求，其响应体中的字段间可能存在某种关联关
系，例如订单相关的测试结果中商品总数和单价的乘积要等于总金额等。
因此，为了对测试结果进行更加准确的评判，本课题提出了测试结果语义评判规则的形式化定义，
用来指导测试结果的评判，测试结果语义评判规则包含响应码语义规则和数据语义规则两部分。
（1）响应码语义规则
响应码规则通过验证测试响应之间的依赖关系是否成立来判定返回响应码是否符合预期。
依赖关系指的是各个测试结果之间的依赖关系，如果将每一个接口视作一个单元，依赖关系可以是

方法间（单元内部）和接口间（单元之间）的依赖关系。其核心在于明确哪些方法或接口的执行结果可
能影响其他方法或接口的行为。通常情况下，这种依赖关系会影响测试用例的执行顺序，以及后续接口
返回的预期响应码。
方法间依赖关系指的是同一个接口内部的不同方法之间的依赖关系。例如，某个接口的 GET 请求可
能依赖于前面执行的 POST 请求的结果，GET 请求的返回结果可能需要 POST 请求成功并返回一定的数
据才能正确执行。接口间依赖关系指的是不同接口之间的依赖关系。在多接口测试中，某些接口的执行
结果可能会影响其他接口的行为。

（2）数据语义规则
数据语义规则主要关注返回数据的合法性以及符合业务逻辑的要求。即使响应码正确，返回的数据
内容仍然需要符合特定的数据语义。例如，某个 GET 请求的返回数据应当符合资源的状态和属性定义，
并满足约定的字段值范围和数据关联关系等约束。如果接口返回的数据不符合这些规则，即使响应码正
确，评判结果也应为不通过。
数据语义规则包含字段值语义规则和数据关联关系语义规则，确保数据符合预期标准并具备逻辑一
致性。字段值检查用于验证返回数据是否符合规定的格式或范围要求，在图 10 的示例中，name 字段的格

（二）从测试响应到评判结果的映射
测试响应的评判过程需要结合多个输入并进行处理，本课题提出基于状态扩展的下推自动机模型
的评判机制，并使用一种形式化的方法对模型进行描述，以实现测试响应的自动化评判。
定义评判模型为 EVA，则有：
EVA = Q, Σ, Γ, G, qst, Zst, qf (1)
下面逐一解释下评判模型中各符号的含义：
（1）Q 的定义
Q 是一个有限的状态集合，定义状态集合如下：
Q = {qst, qres, qrest, qrul, qeva, qf} (2)
其中，qst指初始状态，qres为获取测试响应文件的解析结果状态，qrest为获取 REST 接口文件的解析
结果状态，qrul为获取测试响应语义评判规则文件的解析结果状态，qeva为测试响应评判状态，qf为终止
状态。
在进行测试响应评判时，我们首先根据 REST 接口文件进行语法检查，检查通过后根据评判规则文
件进行语义检查，因此将qeva继续细分为两个状态，即语法检查状态qeva_syn和语义检查状态qeva_sem：
qeva = {qeva_syn, qeva_sem} (3)
在语义检查状态中，又分为响应码检查状态qeva_sem_code和数据语义检查状态qeva_sem_data，即：
qeva_rul = {qeva_sem_code, qeva_sem_data} (4)
普通的下推自动机无法描述出测试响应之间的依赖关系，因此本发明将下推自动机的简单状态进
行扩展以描述测试响应之间的依赖关系，通过引入图结构的方式来实现。状态扩展的下推自动机的状
态转换可以描述出测试响应的评判流程，而状态扩展的依赖关系图可以描述出测试响应之间的依赖关
系。

研究内容二：面向语义的 REST 接口一致性测试结果评判器的设计与实现
面向语义的 REST 接口一致性测试结果评判器作为 REST 接口一致性测试系统中的一个子模块嵌入
进整体系统，评判器作为子模块的主要功能是自动化进行测试结果的评判。
系统主要分为前端、后端以及数据库、被测系统的交互四个部分，前后端、测试系统与被测系统
均通过 HTTP 协议进行通信。而面向语义的 REST 接口一致性测试结果评判器的主要模块为前端的“测

b. 指标设计
为了系统性地、客观地评估本方案的有效性和准确性，对比实验设计了以下两项核心指标：准确
率和故障检测率，这些指标将从不同维度量化本方法在有缺陷和无缺陷测试结果评判中的表现。
在介绍具体指标之前，首先定义评估中使用的四种基本情况分类，这些分类是后续所有计算的基
础，它们描述了评判结果与实际情况之间的关系。
·真阳性（True Positive，TP）：系统正确地将一个“有缺陷”的软件版本识别为“失败”，这代表了成
功的缺陷发现。
·真阴性（True Negative，TN）：系统正确地将一个“无缺陷”的软件版本识别为“通过”，这代表了
系统在正常版本上的稳定性。
·假阳性（False Positive，FP）：系统错误地将一个“无缺陷”的软件版本识别为“失败”，这种情况
通常被称为“误报”，是评估系统干扰性的重要参考。
·假阴性（False Negative，FN）：系统错误地将一个“有缺陷”的软件版本识别为“通过”，这种情况
通常被称为“漏报”，直接关系到系统的缺陷检测能力。
基于以上定义构建了以下两个核心量化指标，分别为准确率和故障检测率。
准确率：准确率是衡量测试系统总体判断正确性的首要指标，即所有测试结果评判中，成功评判
的测试数据占所有测试数据的比例。
·计算公式：准确率 = (TP + TN) / (TP + TN + FP + FN)
·量化方法：该指标将通过计算在所有执行的测试中，被系统正确分类（即真阳性和真阴性）的
版本数量占总测试版本数量的比例来得出，高准确率代表系统整体上具有可靠的辨别能力。
故障检测率：故障检测率是衡量系统发现缺陷能力的关键指标，它专注于评估在所有真实存在的
缺陷中，有多大比例被系统成功地检测出来，直接反映了系统的“查漏”能力。
·计算公式：故障检测率 = TP / (TP + FN)
·量化方法：为了进行更细致的分析，本课题将从两个层面量化此指标。
a) 按缺陷类别划分的故障检测率： 针对 D1 至 D7 中的每一类特定缺陷独立计算其检出率。计算方
法为：该类别中被成功检出的缺陷版本数（TP）除以该类别下所有含缺陷版本的总数（TP + FN），有
助于评估系统对不同类型缺陷的检测是否存在偏向或盲点。

五、问题及整改方案
1. 论文后期工作存在的困难、问题
本课题设计并实现了面向语义的 REST 接口一致性测试结果评判器，顺利完成了对测试结果语义
评判规则的形式化定义及评判器从测试响应到评判结果的映射规则，并最终完成了对测试结果的评
判。但是，因为被测系统有成千上万个，产生的测试结果也各不相同，并且此领域尚且没有学术研究
界公开认可的关于被测系统的测试数据集。
2. 整改方案
目前系统及测试结果评判采用的验证方案是选取信息管理领域典型测试场景，通过在正确的测试
结果中缺陷注入的方式来验证评判器的准确性和可靠性，若评判结果可以准确检测出对应的缺陷，则
说明评判结果是有效的。后续，会考虑加入更加广泛的测试场景以及随机生成测试数据来扩大测试结
果数据集，从而进一步的验证本课题评判方法的可靠性和准确性。
